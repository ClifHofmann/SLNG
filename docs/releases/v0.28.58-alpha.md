# v0.28.58-alpha — Shared Materials, Smarter Graphics Defaults, a Disk Cache Limit, Safer Render Thread

Since v0.28.46-alpha this release is mostly about frame rate and about what happens on a machine you have not tuned yet: a new install picks its graphics preset from the hardware, the asset cache on disk can be capped, a frozen separate render thread now recovers by itself, and mirrors stop costing a second scene when you cannot see them.

## Graphics defaults (FEAT-PERF-26)

- **A new install picks its preset from the machine.** On the first start the viewer reads the dedicated video memory (and treats an integrated GPU as Low), the number of CPU cores and the RAM, and starts on Low, Medium, High or Ultra accordingly. A weak CPU or little RAM caps the preset even with a strong card. An existing installation keeps what it has.
- **Four shadow cascades are Ultra only.** Low, Medium and High now use two. In a crowded region four cascades drew about three times the shadow geometry of two, and cost roughly 5 fps on a render-thread-bound scene. Ultra still uses four, and Graphics › Shadows › Advanced lets you set it by hand.

## Disk cache limit (FEAT-CACHE-01)

- **Preferences › Network & cache › Cache has a size limit** (default 20 GB, 1–64 GB), as the reference viewers have. When the cache reaches the limit, the least recently used files are removed down to 90 % of it; assets in use during the session are kept. Before this the raw asset cache grew without bound (55 GB on one test machine).

## Render thread (BUG-PERF-22, FEAT-UI-81)

- **A frozen separate render thread now falls back by itself.** If the optional separate render thread (Graphics › Performance › Advanced) stops responding, the viewer switches the saved choice back to the main thread and says so on the next start.
- **The notice stays.** Graphics › Performance › Advanced keeps telling you that the render thread was switched off after a freeze, with a **Switch on again** button, instead of a toast that disappears after twenty seconds.
- Why this matters for frame rate: in a crowded region the separate thread roughly doubled the frame rate (14 vs 27 fps in our test), so a silent fallback looks like "the viewer got slow overnight". It no longer is silent.

## Mirrors (BUG-PERF-23)

- **A real-time mirror renders its second scene only while you can see it.** It used to render whenever it was inside the camera cone, even when seen edge-on or from far away, where it covers a sliver of the screen. A mirror now has to take up a visible share of the screen first.

## Textures and materials

- **Anisotropic filtering is 16× again as intended** (BUG-RENDER-52): the project setting stored 16 where the engine expects an index, which asked for far more than 16×. It is now index 4 (16×), with a self-test that guards the value.
- **The D3D12 renderer is still opt-in.** We measured it: about 10 % slower and about twice the video memory of Vulkan on the same scene. Its descriptor-heap limit was raised so it no longer fails on large scenes, but Vulkan stays the default.
- **Faces with the same material now share it** (FEAT-PERF-20, BUG-RENDER-53). Identical prim faces use one material, so the renderer can merge their draw calls. In a crowded region (56 avatars, same spot, same view) that cut draw calls by about 17 %, the render-thread time by about 4 ms, and raised the frame rate from about 26 to about 30. It was an experimental flag before. While making it safe we fixed a bug where foliage stayed white: a surface that left its shared material before its texture arrived got a copy without the texture. Late textures now reach those copies too. `--no-share-materials` turns it off for a comparison.

## For testers and developers

- `--diag` adds `xform=` counters to the performance line (what moves Node3D transforms per frame) and a `[MatAudit]` report that lists textured prim faces wearing no texture.
- An opt-in `--selftest --prim-bench` compares scene nodes against RenderingServer RIDs for prims; its result closed the RID backend (FEAT-PERF-24) as "no gain for frame rate".

## Not yet confirmed in-world

- The hardware-based first-start preset, with a clean user folder, has been exercised by the self-test only.
- The **Switch on again** button and the notice in Graphics preferences are covered by the self-test and unit tests, not by a real freeze.
- The planar mirror change was confirmed for "no second scene out of view"; the in-view case and the edge-on case were measured but are worth another look with a real mirror.
- With shared materials, 3 opaque faces out of about 20,000 still stay without their texture (loaded, but never applied); that case is not understood yet.

## Still missing

- The experimental separate render thread can still freeze the viewer on NVIDIA cards (seen twice). The fallback recovers on the next start; the cause is not found. Keep Render thread on "Main thread" if you want to avoid it.
- About 4 ms of every frame in a crowded region (the part of the scene update that is not avatar animation) is not accounted for yet.
- A landmark list with online status and an "offline" filter (FEAT-UI-78).
- Hundreds of `Leaked unsafe reference` lines for shader materials can appear when the viewer quits after a long session; the cause is not found yet.

## Verification

- Both projects build in Debug and Release.
- **4,041 unit tests green** (335 assets, 2,370 core, 1,336 net; up from 4,004 counted in v0.28.46).
- Self-test green, including new checks for the anisotropy index, the first-start preset, the render-thread notice and the mirror visibility rule.
